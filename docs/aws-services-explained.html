Kallo Analytics Plane

AWS services, explained from zero

This system copies a small, sanitized slice of Kallo's production data from Supabase into AWS once a day, transforms it into dashboard-ready metrics, and serves a private Next.js analytics dashboard continuously on Vercel. The AWS data side stays running cheaply; the ALB/Fargate presentation side is created only for assessment evidence or a live demo.

$50 Total Learner Lab budget. Crossing it deletes the account, so every service has a cost fuse or a teardown plan.
How to read this page: Start with the 30-second table. Then use each service card as a Q&A script: what it is, what our code actually does, why we chose it, and the configuration values worth remembering. The final two sections give you complete demo stories and Learner Lab constraints.

The service-by-service defense guide

The safest exam answer has four parts: define the service simply, point to the concrete resource in this repository, compare it with one realistic alternative, and quote the cost or safety setting that made the choice acceptable.

λ

AWS Lambda

Short-lived Python compute

What it is

Lambda runs one function when an event arrives. AWS starts the runtime, passes in an event object, and stops charging when the invocation finishes. You choose memory and a maximum duration, but you do not patch Linux or keep a process alive.

What it does in this project

The deployed data stack has seven Python 3.12 Lambdas. Six do application work and one is the API authorizer:

  • ExtractFunction reads six allowlisted Supabase views in pages of 1,000, writes JSONL to S3, writes the manifest, and starts Glue exactly once.
  • LoaderFunction runs only after the named Glue job reports SUCCEEDED. It validates every aggregate, writes deterministic metric/date items, and marks manual runs complete.
  • ApiMetricsFunction validates a metric and date range, then performs a DynamoDB Query, never a table scan.
  • ApiRunsFunction starts the extractor asynchronously and returns a UUID, or reads one run's status.
  • ApiAthenaFunction starts or polls one of three fixed Athena query templates.
  • ApiInsightFunction reads seven days of aggregate metrics and asks gemini-2.5-flash for a summary of at most 120 words.
  • AuthorizerFunction compares the supplied bearer token in constant time with the Secrets Manager value.

Why Lambda instead of EC2 or an always-on API server?

These are short, event-driven jobs. Paying for a VPS all day so it can run a daily extract or answer a small number of API calls would add idle cost and patching. Lambda has cold starts and execution limits, so it is not our dashboard web server and it is not the Spark engine. The long-lived Next.js process belongs in a container; the larger transformation belongs in Glue.

Config we chose and why

  • Five functions use ReservedConcurrentExecutions: 1; the read-only metrics function and TOKEN authorizer use 2 so a page bundle and its health probe do not throttle at either Lambda. Total reserved concurrency is 9, below the lab's 10-concurrent-execution ceiling.
  • API Gateway caches each static bearer authorization result for 300 seconds. The Allow policy is wildcarded only inside the current API stage, so one cached decision covers its configured routes. This matches the dashboard aggregate-cache window and removes a Lambda authorizer call from every individual metric read; a rotated token can take up to five minutes to invalidate.
  • Extractor: 512 MB, 300 seconds. It may need multiple HTTPS pages from six views.
  • Loader: 512 MB, 120 seconds. It reads and validates all aggregate files before writing.
  • Metrics, runs and Athena APIs: 256 MB, 30 seconds. Their work is small and mostly remote I/O.
  • Insight: 512 MB, 120 seconds, with its Gemini HTTP call capped at 25 seconds.
  • Authorizer: 128 MB, 10 seconds, result cache TTL 0. Every request is checked against the current token.
  • Every role is the pre-existing LabRole because the Learner Lab forbids creating IAM roles.

“I used Lambda for bounded, event-driven control work. Mutating and expensive functions keep one reserved lane; the read-only metrics function has two, while API Gateway still enforces the spend boundary.”

API

Amazon API Gateway

The spend-sensitive API boundary

What it is

API Gateway gives HTTP paths and methods to backend functions. It can authorize requests, apply rate limits and quotas, and translate an incoming request into a Lambda event. Think of it as the public contract in front of the Python handlers.

What it does in this project

DashboardApi is a regional REST API with six protected operations: GET /metrics/{metric}, POST /runs, GET /runs/{run_id}, POST /athena/query, GET /athena/query/{id}, and POST /insight/weekly. OPTIONS methods provide CORS responses.

The TOKEN authorizer reads Authorization: Bearer .... If valid, it returns an Allow policy and uses the same token as the usage-plan key, so the dashboard does not need to send a second API key.

Why this instead of “just expose the ALB”?

The ALB exposes the visual dashboard. The API can start Glue, run Athena and call Gemini, so it is a separate spend-sensitive surface. API Gateway gives that surface authentication, route-level Lambda wiring, throttling and a monthly quota. A static token is acceptable for one tutor demo, but it is not a production multi-user identity system.

Config we chose and why

  • Endpoint type REGIONAL, stage prod.
  • All real methods use custom authorization and ApiKeyRequired: true.
  • Stage throttle: 2 requests/second, burst 5.
  • Usage plan: 10,000 requests/month, with the same 2-per-second and burst-5 limits.
  • No API cache, which avoids another billable feature and avoids stale run status.
  • Lambda proxy integration keeps request parsing in the handlers and returns normal status/body objects.
Intentional first-load trade-off: dashboard pages request only their required metric subset and space calls by 500 ms. This avoids exceeding the Learner Lab's single-Lambda-execution and API rate limits. Four metrics add a 1.5-second spacing floor; the 12-contract Trace page adds 5.5 seconds before network and cold-start latency. Route loading states keep the shell responsive.
Deployment boundary: the source-controlled six-view, thirteen-metric reduction must be deployed as one coordinated Supabase, extractor, Glue, loader and API revision before production is expected to serve the new contract. Historical E2E findings remain documented separately.

“The ALB publishes the website; API Gateway protects operations that can consume AWS or Gemini budget. The static token, 2-request-per-second throttle and 10,000-request monthly quota fit a single-operator university demo.”

S3

Amazon S3

The data lake and handoff boundary

What it is

S3 stores objects, not mounted disk blocks and not database rows. An object is bytes plus a key such as raw/v_meals/dt=2026-08-13/run=<run-id>/part-0.jsonl. Prefixes look like folders, but the full key is the real address.

What it does in this project

AnalyticsBucket separates pipeline stages by prefix:

  • raw/<view>/dt=YYYY-MM-DD/run=<run-id>/part-<page>.jsonl contains exactly the rows returned by each 1,000-row PostgREST page.
  • raw/_manifests/dt=YYYY-MM-DD/run=<run-id>/manifest.json lists the files and row count for all six views. Glue reads only this declared set.
  • curated/<view>/*.parquet contains the latest complete typed, compressed snapshot written by Spark.
  • aggregates/dt=YYYY-MM-DD/run=<run-id>/<metric>.json contains thirteen dashboard payloads.
  • athena-results/ receives query output generated by Athena.

Why S3 instead of a shared disk or database?

Each pipeline stage can finish by writing durable files that the next stage reads later. S3 is cheap at this scale, works directly with Glue and Athena, and does not require a server. The trade-off is that S3 does not enforce schemas, transactions or joins. The manifest and Glue validation provide our explicit handoff contract.

Config we chose and why

  • Server-side encryption uses AES256, also called SSE-S3.
  • All four public-access-block settings are enabled. This bucket is never a website.
  • Athena results expire after 7 days; incomplete result uploads abort after 1 day.
  • Raw and curated incomplete multipart uploads abort after 7 days.
  • Raw, curated, aggregates and manifests currently have no object-expiration rule, so they persist until the stack or objects are removed.
  • Raw, manifest and aggregate keys include the run ID, so same-day runs remain disjoint. Curated Parquet is intentionally overwritten to prevent Athena from counting one source row once per full snapshot.
  • No EBS volume or gp2 disk is needed. S3 is the persistent storage.

“S3 is the durable boundary between stages. JSONL preserves the landing data, Parquet makes analytical scans efficient, and the manifest stops Glue from accidentally reading half-written or unrelated files.”

DDB

Amazon DynamoDB

Fast keyed state, not a relational database

What it is

DynamoDB is a managed NoSQL database. You design the table around the exact keys your code reads rather than starting from normalized tables and arbitrary SQL. It scales and charges by requests in on-demand mode.

What it does in this project

AnalyticsTable has partition key metric and sort key date, both strings. It stores three shapes:

  • Aggregate: metric=ai_latency, date=2026-08-13, plus a canonical JSON payload.
  • Run guard: metric=_run_guard#pipeline, date=latest, plus the owner and 30-minute guard horizon.
  • Run status: metric=_run#<uuid>, date=latest, plus phases such as queued, extracting, transform_started, completed or failed.

The metrics API queries one metric across a date range. Run guards and run states use exact-key reads. The loader writes the same metric/date key on replay, so the result is idempotent.

Why DynamoDB instead of RDS Postgres?

The design moved away from RDS because these access patterns are simple keyed reads with no runtime joins. RDS would introduce an always-available database lifecycle and, if placed privately while Lambdas need the internet, can lead to a NAT Gateway fixed-cost trap of roughly $32/month before data charges. DynamoDB needs no VPC, no NAT and no stop/start routine, and pay-per-request cost is approximately zero at this demo volume. We lose SQL joins and flexible queries, which is why Glue precomputes the aggregates and Athena handles the occasional SQL-over-files case.

Config we chose and why

  • BillingMode: PAY_PER_REQUEST. No read or write capacity guessing.
  • Encryption at rest enabled.
  • Point-in-time recovery disabled to avoid optional cost in a rebuildable lab system.
  • No secondary indexes and no TTL. The two-key design covers the implemented requests.
  • No VPC configuration, subnet or security group is needed for the Lambda clients.

“DynamoDB fits because every online read is known in advance: metric plus date range, the shared run guard, or run by ID. We traded away relational joins and moved them into the batch transform.”

ETL

AWS Glue

Managed Spark plus the Data Catalog

What it is

Glue ETL starts managed Apache Spark workers for a job, runs PySpark, and releases them when the job ends. Spark is a distributed data-processing engine. The Glue Data Catalog is a separate metadata registry that tells query tools what tables exist and where their S3 files live.

What it does in this project

AnalyticsGlueJob receives --run_id and --manifest_key. It reads only the manifest-listed JSONL files, verifies expected row counts, overwrites each curated view with the latest complete Parquet snapshot, and writes thirteen run-scoped JSON aggregates under aggregates/. The business transformations live in pure Python functions so pytest can run them without Spark.

AnalyticsGlueDatabase creates the catalog namespace, and CloudFormation registers the two external Parquet tables used by Athena.

Why Glue instead of EMR?

EMR would mean choosing and managing a cluster and its lifetime. Glue gives us per-run serverless Spark. Each G.1X worker is 1 DPU; at the cited region rate of about $0.44 per DPU-hour, 2 workers running the full 10-minute ceiling are roughly $0.15 for that run. Actual billing depends on runtime and AWS pricing.

Honest answer: Glue is arguably overkill for only thousands of rows, and the current job even collects each small view to the driver. A Lambda or plain Python job would be simpler. Glue was chosen to satisfy the assignment's Analytics category and to learn Spark. Say that out loud. Examiners usually respect a proportionality argument more than a fake claim that Spark was required.

Config we chose and why

  • Glue 4.0, command glueetl, Python 3.
  • WorkerType: G.1X, NumberOfWorkers: 2. This is the lab minimum chosen for the job.
  • Timeout: 10 minutes, MaxRetries: 0, MaxConcurrentRuns: 1. These are cost fuses.
  • Overwrite-mode curated snapshots; no extraction-date partition is retained because every extraction is already a full snapshot.
  • LabRole is the job role because custom IAM roles are blocked.
Catalog implementation: CloudFormation creates AWS::Glue::Table resources for v_meals and v_pipeline_runs. Each external table maps directly to the corresponding latest-snapshot Parquet prefix, so no crawler, partition projection or MSCK REPAIR TABLE step is required.

“Glue gives us disposable Spark rather than a managed EMR cluster. It is intentionally bounded to two G.1X workers, one concurrent run, zero retries and ten minutes, and I acknowledge that Spark is educational rather than necessary at our current row count.”

SQL

Amazon Athena

SQL that scans S3 on demand

What it is

Athena runs SQL without a database server or warehouse cluster. It uses catalog metadata to understand table columns and scans the underlying S3 files when a query runs. Cost is mainly based on bytes scanned.

What it does in this project

AnalyticsWorkGroup is the cost boundary. The Athena Lambda accepts only three template IDs: macro percentiles by date, meals by preferred locale, and p50/p95 pipeline latency by model. User input is limited to validated ISO dates, so callers cannot submit arbitrary SQL.

The API is asynchronous: POST returns a query_execution_id, GET polls status, and a successful poll returns at most 100 result rows. Athena writes results to athena-results/.

Why Athena instead of Redshift?

Redshift is a data warehouse with running capacity to size and pay for. Athena charges per TB scanned over files and has no cluster to keep alive, which fits rare demonstration queries. It is slower and less predictable than an always-warm warehouse, and badly partitioned or broad queries can scan too much data. Parquet, fixed templates and the workgroup cap control that risk.

Config we chose and why

  • BytesScannedCutoffPerQuery: 1073741824, exactly 1 GiB.
  • EnforceWorkGroupConfiguration: true, so a client cannot bypass the output and cost settings.
  • Query results use SSE-S3 encryption and expire from S3 after 7 days.
  • CloudWatch workgroup metrics are enabled.
  • Only fixed SQL templates are exposed; dates become validated DATE literals.
Latest-snapshot trade-off: the clean stack creates all three catalog tables over fixed curated prefixes. This removes crawler cost, partition-update lag and duplicate counts across full snapshots; the trade-off is that Athena exposes the latest successful curated state rather than historical extraction versions.

“Athena is our bounded exploratory SQL path, not the normal dashboard database. We pay only when a fixed query scans Parquet, and the enforced workgroup stops any query above 1 GiB.”

EVT

Amazon EventBridge

Schedule and service-event wiring

What it is

EventBridge can fire on a schedule or match events emitted by AWS services. When a rule matches, it sends the event to a target such as Lambda. It replaces a small amount of cron and polling-server code.

What it does in this project

DailyExtractRule invokes the extractor with rate(1 day). GlueSucceededRule listens for a Glue Job State Change where both the job name matches AnalyticsGlueJob and state equals SUCCEEDED, then invokes the loader. Lambda resource policies allow only those scoped rules to invoke their functions.

Why EventBridge instead of cron, Step Functions or polling Glue?

There is no always-on machine on which to install cron. The pipeline is linear enough that Step Functions would add another orchestration layer without much value. Glue already emits a success event, so polling its status would waste calls and code. EventBridge does not provide the rich visual workflow and retry state that Step Functions would, so failures currently live in service logs rather than a workflow state machine.

Config we chose and why

  • Daily schedule is rate(1 day). It is a 24-hour cadence from rule creation or update, not “midnight UTC.”
  • Both production rules are enabled.
  • The Glue rule matches the exact job and only SUCCEEDED, so the loader never intentionally reads incomplete output.
  • The probe stack includes the same daily schedule in DISABLED state to test wiring without recurring cost.
  • No dead-letter queue or failure rule is configured.

“EventBridge owns time and service events. One rule replaces cron; the other reacts to the exact Glue success event, so the loader never has to poll and never starts on a failed job.”

ECS

Amazon ECS with AWS Fargate

The disposable dashboard runtime

What it is

ECS is the service that describes containers, starts them, replaces unhealthy tasks and keeps a desired count running. Fargate is the compute mode: AWS supplies the host, so there is no EC2 instance to select, patch or SSH into.

What it does in this project

DashboardCluster contains one DashboardService with desired count 1. The task pulls the Next.js image from ECR, receives API_BASE_URL as a normal environment variable, receives DASHBOARD_TOKEN directly from Secrets Manager, and sends logs to a 7-day CloudWatch log group.

The presentation stack is created by scripts/lab-up.sh for a work session and deleted by scripts/lab-down.sh afterward. This is teardown-to-zero between sessions, not automatic autoscaling to zero while the stack exists.

Why Fargate instead of Elastic Beanstalk or EC2?

EC2 would require a VM lifecycle, OS patching and container process management. Beanstalk can manage an application environment, but it hides more infrastructure behavior and still creates an environment that must be understood and cleaned up. Fargate directly runs the Docker artifact with no host administration, while ECS gives explicit task, service, network and health settings.

Config we chose and why

  • Task size 256 CPU units and 512 MiB, the smallest configured Fargate size.
  • DesiredCount: 1, launch type FARGATE, platform LATEST.
  • RuntimePlatform: X86_64 / LINUX. Apple Silicon defaults to ARM builds, so docker build --platform linux/amd64 pins a compatible image.
  • awsvpc networking and a public IP in two default-VPC public subnets. This avoids a NAT Gateway.
  • The task security group accepts traffic only from the ALB security group.
  • LabRole is both task role and execution role because the lab forbids creating dedicated roles.
  • No EBS or gp2 volume. The container is disposable and persistent data lives in AWS services.
Implemented network path: the task definition, ECS service and target group all use application port 3000. The task security group admits that port only from the ALB security group, and the target group checks /api/health, keeping public port 80 at the listener while aligning the private hop with the Next.js container.

“ECS defines the desired container state and Fargate supplies the host. We use one 0.25-vCPU, 512-MiB x86 task only during sessions, then delete the whole presentation stack.”

ALB

Application Load Balancer

The temporary public front door

What it is

An ALB receives HTTP requests, checks which backend targets are healthy, and forwards traffic. “Application” means it operates at HTTP level rather than merely forwarding raw network packets.

What it does in this project

DashboardLoadBalancer is internet-facing and IPv4. Its listener accepts HTTP on port 80 and forwards to DashboardTargetGroup. The target type is ip, which is required for Fargate tasks using awsvpc. Health checks request / and accept status 200 through 399.

The ALB security group allows public port 80. The task security group allows its application port only when the packet came from the ALB security group.

Why ALB instead of CloudFront?

CloudFront is blocked in AWS Academy Learner Lab. ALB is the supported layer-7 front door and integrates directly with an ECS IP target group. CloudFront would be a CDN and edge cache, which is useful for global static delivery but not required for one regional tutor demo. ALB has an hourly cost, so it lives in the disposable stack.

Config we chose and why

  • Two public subnets in different Availability Zones, discovered from the existing default VPC by lab-up.sh.
  • Internet-facing, IPv4, one HTTP listener.
  • IP target group with / health check and a 200-399 matcher.
  • Fargate health-check grace period 60 seconds.
  • No domain, certificate, HTTPS listener or WAF is configured. The current stack output is an http:// ALB DNS URL.
Aligned routing: the public listener receives HTTP on port 80, then forwards to the IP target group on port 3000, matching the ECS service and container port. Health checks use /api/health, and the service security group accepts port 3000 only from the ALB security group.

“ALB is our session-only HTTP reverse proxy and health router. CloudFront is unavailable in the lab, and the ALB is deleted after the demo to stop its hourly cost.”

ECR

Amazon Elastic Container Registry

The private dashboard image store

What it is

ECR stores Docker-compatible image layers and tags inside an AWS account and region. ECS pulls the image URI from ECR before it can start a task.

What it does in this project

scripts/push-image.sh builds dashboard/ for linux/amd64, creates the kallo-dashboard repository if it does not exist, enables scan-on-push, logs Docker into the registry, pushes the tag, and writes IMAGE_URI to the ignored .lab-config. lab-up.sh passes that URI into the task definition.

Why ECR instead of Docker Hub?

ECR is private, region-local and integrated with ECS task image pulls. It avoids depending on an external public registry or its pull limits. The trade-off is AWS authentication and stored-image cost. Images persist after lab-down.sh, so they need deliberate cleanup if tags accumulate.

Config we chose and why

  • Repository name defaults to kallo-dashboard; tag defaults to latest but the demo guide uses named tags such as first-demo.
  • Image scanning is enabled when the script creates the repository.
  • Build command pins --platform linux/amd64 to prevent Apple Silicon from producing an ARM-only image.
  • ECR is script-managed, not declared in CloudFormation.
  • The repository and images are intentionally not deleted by lab-down.sh.
Learner Lab detail: LabRole can pull images for ECS but is read-only for ECR pushes. The operator must run aws ecr get-login-password with current federated session credentials. When the lab session expires, log in again and repeat the push authentication.

“ECR is the private handoff between my laptop build and Fargate. I pin amd64, push with temporary federated session credentials, and let the task pull through LabRole.”

SEC

AWS Secrets Manager

Credentials outside source and images

What it is

Secrets Manager stores sensitive strings and returns them only to authorized AWS identities. Code keeps an ARN or environment variable reference, while the secret value stays outside Git and the container image.

What it does in this project

The persistent stack creates three secrets:

  • SupabaseCreds stores the project URL and restricted analytics key as JSON. The extractor retrieves it at runtime.
  • GeminiKey stores the Gemini API key. The insight Lambda reads it on the first invocation of a warm environment and caches it in memory.
  • DashboardToken stores the static bearer token. The authorizer reads it; ECS injects the same value as DASHBOARD_TOKEN.

Why not put secrets in code or ordinary environment values?

Hard-coded keys leak through Git history, ZIP files and images. Plain CloudFormation environment values are visible as configuration. Secrets Manager keeps the stored value behind an ARN and supports runtime retrieval or ECS secret injection. It does not automatically make the static token multi-user or rotate it; rotation is manual here.

Config we chose and why

  • Template parameters use NoEcho: true, so normal CloudFormation output does not print their values.
  • Dashboard token length is constrained to 20-128 characters.
  • Supabase, Gemini and dashboard credentials are separate secrets to avoid accidental coupling.
  • Secret values are passed at deployment from shell environment variables and never committed.
  • LabRole performs reads because the lab does not allow a custom least-privilege role.

“Secrets Manager prevents keys from entering Git, Lambda packages or the image. The application holds only secret ARNs, and values arrive through runtime reads or ECS secret injection.”

CFN

AWS CloudFormation

Infrastructure as reproducible stacks

What it is

CloudFormation reads a template, creates resources in dependency order, updates changed resources, and can delete the whole group as a stack. It turns console clicking into reviewable infrastructure as code.

What it does in this project

There are three templates:

  • infra/probe-stack.yaml is a disposable Session-0 permission test: one tiny Lambda, one disabled schedule, one two-worker Glue job, one Athena workgroup and a harmless secret.
  • infra/data-stack.yaml is persistent and cheap: S3, DynamoDB, Glue job/database, Athena workgroup, seven Lambdas, API Gateway, EventBridge and three secrets.
  • infra/presentation-stack.yaml is disposable: ALB, target group, security groups, ECS cluster/service/task and a 7-day log group.

deploy-data-stack.sh deploys the data template and then replaces its seven inline placeholder functions with ZIPs from the repository. lab-up.sh and lab-down.sh create and delete the presentation stack.

Why CloudFormation instead of manual console setup?

The $50 Learner Lab can delete the whole AWS account after an overrun, and sessions provide temporary credentials. Infrastructure as code is therefore disaster recovery: after obtaining a fresh lab, one scripted deployment per stack recreates named resources and safety settings consistently. Operator inputs still matter: secrets, deployment-bucket URI, image URI and default-VPC IDs are not magically recoverable.

Config we chose and why

  • Every template targets the operator-selected region; all scripts default to us-east-1.
  • No template contains AWS::IAM::Role or AWS::IAM::Policy. Role ARNs point to LabRole.
  • Cross-stack exports give the presentation stack the API URL and dashboard secret ARN.
  • The default VPC and two public subnet IDs are parameters, so the template creates no VPC.
  • The data and presentation stacks are separated so expensive session resources can be deleted without deleting data.
  • ECR creation remains in push-image.sh, outside CloudFormation, and Lambda application ZIP updates happen after stack deployment.

“CloudFormation is both repeatability and budget control. The persistent and disposable tiers are separate stacks, so I can tear down the ALB and Fargate task after every session and rebuild consistently after a lab reset.”

Two flows to narrate in the demo

Point at the runtime diagram while speaking. Name the handoff object or key at every step. That proves you understand how the services connect rather than merely recognizing their icons.

The unattended daily pipeline

  1. EventBridge invokes the extractor once every 24 hours with rate(1 day).
  2. The extract Lambda reads Supabase over HTTPS. It reads only six sanitized operational views, asks for explicit columns, and pages each complete snapshot 1,000 rows at a time in deterministic order. It keeps no DynamoDB watermark.
  3. S3 receives raw JSONL. Each page becomes raw/<view>/dt=<date>/run=<run-id>/part-<n>.jsonl. If all six views finish, Lambda writes one run-scoped manifest containing file names and row counts.
  4. Lambda starts Glue exactly once. It passes the run ID and manifest key. A partial extraction never produces a manifest and never intentionally starts Glue.
  5. Glue transforms the declared files. Two G.1X workers validate counts, overwrite the latest complete curated Parquet snapshot, and compute thirteen run-scoped aggregate JSON files.
  6. Glue emits success; EventBridge filters it. Only SUCCEEDED for this exact job invokes the loader.
  7. The loader writes DynamoDB idempotently. Each payload goes to (metric, date). Replaying the same date replaces the same keys rather than duplicating records.

A page load and “Run now” click

  1. The browser normally requests the Vercel production URL. For assessment evidence, the disposable ALB listener on port 80 forwards to the Fargate target and container on port 3000.
  2. Next.js renders the product and diagnostic console. Each route requests only its allowlisted metric subset through a same-origin proxy, selects the newest full snapshot, and keeps the bearer token server-side.
  3. API Gateway authorizes and throttles. The TOKEN Lambda checks the bearer secret, then the metrics Lambda queries DynamoDB by metric and date range.
  4. Next.js selects the newest complete payload. It never merges multiple loader dates, because every aggregate object is already a full snapshot. Per-metric errors remain independent from successful empty results.
  5. The operator selects Run pipeline now. The browser calls the same-origin Next.js route, which calls POST /runs through API Gateway.
  6. The runs Lambda returns quickly. It atomically claims the 30-minute shared DynamoDB guard, records a queued UUID, and asynchronously invokes the extractor. The browser receives HTTP 202 instead of waiting minutes; competing starts receive HTTP 429.
  7. The browser polls every 5 seconds. GET /runs/{run_id} reads _run#<uuid>/latest from DynamoDB until the loader changes the phase to completed. The runs Lambda writes the initial queued record before asynchronous invocation, so the first poll has a stable item.

The Learner Lab reality

These are not side notes. They explain several architecture choices that would look unusual in a normal company AWS account.

$50 kill-switch

Exceeding the total budget deletes the AWS account. Glue has time, retry and concurrency fuses; Athena has a 1 GiB scan fuse; API Gateway has rate and monthly limits; ALB and Fargate are session-only.

us-east-1 only

Every deployment script defaults to us-east-1. ECR images, Glue jobs, Lambdas, stacks and lookups must stay in the same intended region.

LabRole only

The lab forbids creating IAM users, roles and policies. Lambda, Glue, ECS task execution, ECS application calls and EventBridge targets all reference the supplied LabRole. This is compliant but broader than production least privilege.

No CloudFront or Cognito

ALB replaces the unavailable CDN/front door. A static bearer TOKEN authorizer replaces unavailable Cognito for one known operator. That is a demo security model, not customer identity.

ECR push uses session credentials

ECS can pull with LabRole, but the role is read-only for pushes. Docker login and push use the operator's current federated credentials. Expired credentials require a new lab session and login.

Session expiry is not teardown

Console and CLI credentials expire, but S3, DynamoDB, secrets, ECR images, ALBs and running Fargate tasks persist and can still cost money. End Lab is not a substitute for scripts/lab-down.sh.

No NAT Gateway

Lambda and managed data services stay outside a VPC. The Fargate task gets a public IP in default-VPC public subnets, but its inbound rule trusts only the ALB security group. This avoids the roughly $32/month NAT fixed-cost trap.

Probe before the real stack

The probe checks that LabRole, PassRole, secret reads, Lambda, Glue and Athena work in this lab. Delete kallo-probe when those one-time checks pass.

Supporting AWS pieces you will also be asked about

IAM and LabRole
IAM decides who may call which AWS action. This repository cannot create least-privilege roles, so it supplies the existing LabRole ARN everywhere a service identity is required.
Default VPC and public subnets
The VPC is the private network boundary for ALB and ECS. lab-up.sh discovers the existing default VPC and two public subnets in different Availability Zones.
Security groups
Stateful virtual firewalls. One allows the public to reach ALB port 80; the other allows task traffic only when its source is the ALB security group.
CloudWatch
AWS logging and metrics. The dashboard has a 7-day ECS log group, and metrics are enabled for API Gateway, Athena and Glue. There are no alarms, dashboards or explicit Lambda log-retention resources.
Glue Data Catalog
The schema directory Athena needs to map table names to S3 Parquet. CloudFormation creates the database and the three fixed external tables used by the Athena templates.
EC2
No EC2 instance is created. Fargate supplies container compute, Lambda supplies function compute, and Glue supplies Spark compute. That removes server patching and EBS volume choices.
A defensible final summary: “I separated a persistent, mostly pay-per-use data plane from a disposable presentation plane. The data path is event-driven and file-based; the online API reads precomputed DynamoDB aggregates. Every expensive or user-triggered path has a limit, and the entire environment is reproducible from templates and scripts.”

Glossary for the live Q&A

IAM role
A set of AWS permissions assumed by a service or task. It is an identity, not a server.
ARN
Amazon Resource Name, the globally structured identifier for an AWS resource, such as the LabRole or a secret.
Stack
A group of resources created, updated and deleted together by CloudFormation.
Workgroup
An Athena policy boundary that enforces query output, monitoring and byte-scan limits.
DPU
Data Processing Unit, Glue's compute unit. A G.1X worker provides 1 DPU.
Full snapshot
A complete bounded copy of every allowlisted source view for one run. This project deliberately keeps no extraction watermark.
Manifest
A small JSON contract listing exactly which raw files and row counts belong to one pipeline run.
Idempotent
Safe to repeat with the same input. The loader overwrites the same metric/date key rather than creating duplicates.
Cold start
The extra first-invocation time while Lambda creates a fresh runtime environment.
VPC
Virtual Private Cloud, an isolated AWS network containing subnets and security rules.
Subnet
A slice of VPC address space in one Availability Zone. A public subnet has a route toward an internet gateway.
Security group
A stateful virtual firewall attached to an ALB or task network interface.
Target group
The registered backend addresses and health-check rules to which a load balancer forwards traffic.
Task definition
The ECS recipe for an image, CPU, memory, ports, roles, environment, secrets and logging.
PostgREST
The HTTP API layer Supabase exposes over Postgres. The extractor uses Range headers, filters and explicit column selection.
